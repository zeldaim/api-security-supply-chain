# 명세 밖 호출 분류 (offspec_triage)

OpenAPI 에 없는 (메서드, 경로) 호출을 다룬다. **명세에 없다는 사실만으로 위험하다거나 악성이라고 정하지 않는다.**
명세 밖 호출은 조사를 시작하는 신호로만 쓰고, 우선순위는 아래 세 가지로 정한다.

| 축 | 어디서 | 보는 것 |
|---|---|---|
| 승인 상태 | 기준선 CSV `decision` | active · review · deprecated · remove · 없음(미등록) |
| 소유권 | 기준선 CSV `owner` | 책임질 사람·팀이 있는가 |
| 사용 맥락 | 접근 로그 · 앱 로그 | 실제로 응답하는 경로인가, 누가(정상 이용 이력 / 탐색 흔적 / 내부·외부) 얼마나 꾸준히 부르나, 프런트가 부르나, 명세에 있는 경로의 다른 메서드인가 |

이전 단계와의 관계:

- 팀 초기 생성기(`automate/rules/gen_shadow_rules.py`)는 명세에 없으면 모두 경보를 낸다.
- 기준선 v2 + 승인 대시보드(`standardize/inventory/`)는 active 만 허용 목록에 넣는다. 그래서 review · deprecated · 미등록이 모두 같은 경보가 되고, 소유자와 사용 맥락은 쓰지 않는다.
- v3 일반 기준(`judge.py`)은 일부러 의도(승인)를 빼고 G1 "명세 밖 + 관측 = 위반(높음)"으로 판정한다.
- 이 단계는 위 셋을 바꾸지 않는다. 그 사이에서 명세 밖 호출을 **상태와 우선순위로 나누는 일**만 한다.

## 실행

```bash
python standardize/policy/offspec_triage.py \
  --spec openapi.yaml --baseline baseline_v2.csv \
  --log app.log --log access.log.gz \
  [--internal 10.0.0.0/8] --out-dir out/
python standardize/policy/test_offspec_triage.py      # 판정표 시나리오 시험 13개
```

| 출력 | 내용 |
|---|---|
| `offspec_triage.csv` | 실제로 있거나 있을 수 있는 명세 밖 (메서드, 경로) — 우선순위 · 분류 · 위험·완화 요인 · 조치 |
| `offspec_notfound.csv` | 404·405 만 받은 경로 (자산 아님) |
| `offspec_callers.csv` | 출발지별 명세 경로 2xx 수, 404 받은 서로 다른 명세 밖 경로 수 |
| `offspec_report.md` | 사람용 요약 |
| `offspec_allowlist.yaml` | "명세 누락(승인·소유자 있음)" 만 — `gen_shadow_rules.py --allowlist` 형식 |

로그는 Apache combined 형식과 JSON 줄(`method` · `path` · `status` · `client_ip`/`ip` · `timestamp`)을 모두 읽는다. `.gz` 도 된다.

## 판정표

### 1단계 — 실제로 있는 경로인가 (응답 코드)

| 판정 | 조건 | 처리 |
|---|---|---|
| 있음 | 2xx·3xx 가 한 번이라도 있음 | 2단계로 |
| 없음 | 2xx·3xx 는 없고 404·405 가 있음 | 자산이 아님 → `offspec_notfound.csv`. 섞여 있는 401·500 은 라우팅 전 단계(인증 미들웨어·WAF·페이로드 오류)의 응답으로 본다 |
| 불명 | 401·403·400·422·5xx 만 있음 | 미등록이면 "존재 불명"(낮음). 인증된 요청으로 다시 확인 |

### 2단계 — 승인 상태 × 소유자 → 기본 우선순위

| 승인 상태 | 소유자 있음 | 소유자 없음 |
|---|---|---|
| active | **명세 누락** — 정보 (명세 추가 요청, 예외 목록에 들어감) | **승인됐으나 소유자 없음** — 낮음 |
| review | 검토 중 — 낮음 | 검토 중 — 중간 (+ 위험 요인 "소유자 없음") |
| deprecated | Zombie — 중간 | Zombie — 중간 (+ "소유자 없음") |
| remove | 제거 결정인데 응답 — **높음 고정** | 같음 |
| 미등록 | — | 미등록 (Shadow 후보) — 중간 |

### 3단계 — 사용 맥락으로 한 칸 조정

**우선순위 = 기본 + 1(위험 요인이 하나라도 있으면) − 1(완화 요인이 하나라도 있으면)**

| 위험 요인 (+1) | 완화 요인 (−1) |
|---|---|
| 소유자 없음 (review · deprecated) | 프런트엔드가 부름 (기준선 `frontend=y`) |
| 관리·내부·대량 조회 성격의 경로 이름 (admin · debug · internal · export · dump · /all …) | 정상 이용 이력이 있는 출발지 3곳 이상이 2개 이상 시간대에 걸쳐 부름 |
| 읽기 경로에 쓰기 메서드가 응답 (명세에 있는 경로의 다른 메서드) — **이 요인이 있으면 완화하지 않음** | 내부 출발지에서만 호출 (`--internal` 을 줄 때만) |
| 성공 응답이 탐색 흔적 출발지에서만 나옴 | |
| 외부 출발지에서 성공 응답 (`--internal` 을 줄 때만) | |

- **정상 이용 이력:** 명세 경로에서 2xx 를 3번 이상 받은 출발지
- **탐색 흔적:** 서로 다른 명세 밖 경로 5개 이상에서 404 를 받은 출발지. 둘 다 해당하면 탐색 흔적으로 본다.
- **하한과 상한:** active+소유자는 사람이 승인한 것이라 올리지 않고 "재확인 권장"만 적는다. review · deprecated · 미등록은 판정이 끝나지 않았으므로 '정보'로 내리지 않는다.
- 문턱값은 `--min-ok` · `--probe-paths` · `--min-clients` · `--min-hours` 로 바꾼다.

## 검증

| 데이터 | 결과 |
|---|---|
| 시나리오 시험 (가짜 로그, `test_offspec_triage.py`) | 판정표의 13개 경우 모두 통과 |
| **팀 웹 실제 로그** — app.log 361,022줄 (2026-10-26~11-03), 기준선 v2, 팀 명세 16개 | 명세 밖 (메서드, 경로) 193,214개 중 **193,199개(277,460회)는 404·405 만 받은 없는 경로** — 대부분 스캐너 출발지 1곳. 실제로 응답한 것은 **2개뿐이고 둘 다 높음**: `GET /api/v1/users/{id}` (BOLA 실증) · `GET /api/v1/diagnostics/ping` (RCE). 둘 다 review·소유자 없음. 나머지 13개는 존재 불명(낮음, HEAD·OPTIONS 등) |
| crAPI run3 (정상 16,748줄 + 공격 219줄) | 정상 트래픽의 명세 밖 호출 0. 탐색 공격 12경로 중 10개는 없는 경로, 탐색 흔적 출발지 1곳 식별 |

팀 초기 생성기 기준으로는 위 277,460회 전부가 같은 "명세 밖" 경보 대상이다.

## 한계

- **완화 쪽은 실제 데이터로 확인하지 못했다.** 팀 기준선에는 엔드포인트 소유자가 하나도 없고, crAPI 정상 트래픽에는 명세 밖 호출이 없다. "승인·소유자 있음", "정상 이용으로 낮춤" 경우는 시나리오 시험으로만 확인했다.
- 명세 템플릿이 넓으면 명세 밖 경로가 흡수된다. crAPI 의 `/workshop/api/shop/orders/export` 는 `/orders/{id}`, `/community/api/v2/community/posts/all` 은 `/posts/{postId}` 로 맞춰져 명세 안으로 잡힌다. 이런 호출은 ID 열거(BOLA) 룰이 맡는다.
- 응답 코드로 존재를 판단하므로, 없는 경로에도 200 을 돌려주는 앱(SPA 폴백 등)에서는 1단계가 틀린다. 그런 앱은 `--scope` 로 API 접두어만 보게 한다.
- 출발지는 IP 기준이다. NAT·프록시 뒤에서는 여러 사용자가 한 출발지로 보인다.
- Wazuh 룰은 아직 이 우선순위로 나뉘지 않는다. 지금은 "명세 누락(승인·소유자 있음)"만 예외 목록으로 넘겨 경보를 끄고, 나머지는 기존 룰 수준으로 경보를 낸다.
