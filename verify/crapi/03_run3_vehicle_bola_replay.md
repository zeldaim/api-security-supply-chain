# crAPI 3차 실행 — 차량 BOLA · 공개 데이터 재생 정상 (2026-11-16, 완료)

> 2차 실행([`../crapi_generality_2026-11-15/`](../crapi_generality_2026-11-15/README.md))과 코드 수정([`../v2_portable/`](../v2_portable/README.md)) 뒤 남은 세 가지를 한 번에 봤다.
>
> **결과 (§6):**
> 1. **게이트 통과.** 정상 150분을 끊김 없이 모아, 규칙 정상 모델(A)과 규칙+재생 모델(B) 모두 평가 게이트를 통과했다.
> 2. **UUID 열거(차량 위치 BOLA) 탐지 확인.** 남의 차량 20대 위치가 실제로 200 으로 반환됐고, 느린 것·빠른 것 모두 탐지됐다.
> 3. **규칙 기반 정상만으로 학습한 모델은 사람 속도의 정상을 거의 전부 오탐한다** (재생 정상 120창 중 115창 high). 재생 정상을 학습에 넣으면 3창으로 줄고, 실제 공격 17창 중 15창 high · 1창 medium 을 유지한다.

## 2. 생성기 v3 에서 바뀐 것

- **차량 등록:** 가입 환영 메일(mailhog)의 VIN·Pincode 로 차량을 등록한다. 게시글 작성자 정보에 차량 ID(UUID)가 실려, 공격자가 그것을 모아 남의 차량 위치를 조회할 수 있다(crAPI 의 실제 취약점). 시험 실행에서 4대 조회 4건 모두 200.
- **정비 요청:** 정상 사용자가 가끔 정비 요청을 낸다 → 정비 보고서가 실제로 생긴다 → 보고서 BOLA 가 오류 없이 200 으로 돌아온다(2차에서는 400 이 섞여 오류 때문에 걸렸다).
- **재생 모드:** 아래 §3.

## 3. 공개 데이터 재생 — 대응표

| 출처 (라이선스) | 이벤트 | crAPI 요청 |
|---|---|---|
| OTTO (CC BY 4.0) | `clicks` · `carts` | `GET /workshop/api/shop/products` (crAPI 에 상품 상세·장바구니가 없어 상점 화면으로 합침) |
| | `orders` | `POST /workshop/api/shop/orders` + `GET …/orders/all` (잔액 한도라 8건까지, 넘으면 주문 내역 보기) |
| Stack Overflow 세션 (CC BY 4.0) | `POST_QUESTION` | `POST /community/api/v2/community/posts` |
| | `POST_ANSWER` · `COMMENT` | 글 읽기 + `POST …/posts/{id}/comment` |
| | `EDIT_*` · `VOTE_*` | `GET …/posts/{id}` (글 읽기) |

- **데이터에서 가져온 것:** 세션 안 요청 간격, 행동 종류의 순서와 비율.
- **규칙으로 채운 것(데이터에 없음):** 방문 시작 화면(`/`, 대시보드), 차량 화면(방문의 20%), 한 사용자가 상점 세션과 커뮤니티 세션을 번갈아 하는 것(세션을 무작위로 고름), 어떤 글·상품을 고르는지.
- **시간 압축:** 세션 안 간격이 300초를 넘으면 300초로 줄였다(OTTO 21%, Stack Overflow 40% 의 간격이 해당). 세션 사이에는 30~180초 쉰다. 실제 데이터는 며칠에 걸쳐 있어 150분 안에 넣으려면 줄일 수밖에 없다.
- 원본 분포: OTTO 간격 중앙값 49초(p25 20초), Stack Overflow 201초 — `build_replay_output.txt`.
- 재생 사용자는 요청이 드물어 5분 창에 요청 5건 미만인 창이 많을 것이다(판단 불가로 빠짐). 창 수는 결과에 적는다.

### 6-5. 이 결과로 말할 수 있는 것 / 없는 것

**말할 수 있음**
- v2 워크플로는 crAPI 에서 설정만으로 끝까지 돌고 게이트를 통과한다(데이터가 충분하면).
- 숫자 경로 ID · 쿼리 ID · UUID 세 형태의 BOLA 열거가 모두, 느린 경우까지 탐지된다. 2차에서 "오류 때문에 걸렸다"던 보고서 BOLA 는 오류 없이도 걸린다.
- 스크립트 생성기 정상만으로 학습하면 사람 속도의 정상 사용자를 거의 전부 이상으로 본다. `ml_detection` docs/35 의 결과(생성기만 학습 → 재생 정상 오탐 14~26%)와 같은 방향이고 정도는 훨씬 심하다.
- 재생 정상을 학습에 넣으면 그 오탐이 사라지고 공격 탐지는 거의 유지된다.

**말할 수 없음**
- 실제 서비스의 오탐률. 재생 정상도 "실제 사람의 간격·행동 비율 + 내가 정한 대응 규칙"이고, 300초 초과 간격은 줄였다. 정상 사용자는 여전히 남의 주문·차량·보고서를 열지 않는다.
- B 의 재생 정상 오탐(3/120)을 "처음 보는 사람"의 오탐으로 읽는 것. 재생 창의 대부분이 B 의 학습에 들어갔다. 처음 보는 시간대 기준으로는 검증 94창 중 high 0 · medium 2 다.
- C(재생만)의 탐지 성능. 학습 창이 105개뿐이라 판단할 수 없다.
- 공격은 종류당 1회다. 창 17개의 결과다.
- Shadow API 룰은 이번 로그로 다시 logtest 하지 않았다(룰 내용이 `../v2_portable/crapi_run_2026-11-16/` 과 같다).
